## Found in M105 beyond the review

- **An ffmpeg that ended during its own start was never handled (part C).** Production v2.1.0 on
  2026-10-02 10:24 UTC, right after a playout container restart: a YouTube pair started at 10:24:10, the
  cycle 15 s later logged `playout.boundary.fallback_bridge` naming that same item, then
  `playout.stop.deadline_exceeded` (switch); the fallback aired 3 s and the next archive followed. Still on
  `main`: the playout's exit and stderr handlers were attached only after the start's awaited writes, so
  an exit in that window had no listener (the M76 as-run watcher already said so). The handle stayed on the
  dead child; the selection called it on air (not `killed`), the boundary found no running process
  (`exitCode` set) and bridged for it, and the switch waited 20 s for an exit that had already happened.
  Fixed: both handlers attached before the first await, the start write and the success incident skip a
  child already gone, a stop of an ended child returns at once (`playout.stop.already_exited`), the
  selection's "on air" uses the boundary's test, and the cycle-end write keeps an exit status written
  before it (`decideCycleEndStatus`), so the item is owed its M94 retry (`tests/unit/playout-early-exit.test.ts`). The log lines
  fit this path; that the item really ended at once (rather than hung) is not proven from them. v2.1.0
  has no as-run log; its playout log would show it, if that container's log still exists: no
  `playout.process.exit` and no `playout.ffmpeg.stderr` line between the start at 10:24:10 and the bridge
  (both handlers were not attached yet). The uplink attaches its exit handler after
  awaits too; its running list and its stop check `exitCode`, so it does not wedge, but such an exit goes
  unlogged (not changed).
